> 事实基线：`AGENTS.md`（唯一事实基线，约束冲突时以其「硬性约束」为准）｜`docs/01-案例调研与技术选型.md`｜`docs/02-私人记忆库设计.md`｜`software_prompts/02-architecture.md` ARC-01

## 0. 输入摘要（决策依据）

**业务背景**：Prompt Pad 是常驻 Windows 系统最上层、全局热键 `Ctrl+Space` 唤起、带私人记忆的提示词优化 Pad。两个待定决策点：①外壳框架：Tauri 2 vs Electron（降级方案）vs PyQt/PySide；②本地嵌入模型：`multilingual-e5-small`（~117MB / 384 维，ONNX 本地推理）vs `bge-m3`（~570MB+ / 1024 维，ONNX 本地推理）。

**候选方案（固定 5 个）**：①Tauri 2（React 18 + TypeScript + Vite + Tailwind CSS 前端 + Rust 后端）②Electron（仅作降级方案）③PyQt/PySide ④`multilingual-e5-small` ⑤`bge-m3`

**硬性约束（AGENTS.md 原文）**：

- 「外壳 | Tauri 2，**禁止 Electron**（除非某 Windows 能力绝对必需）」
- 「前端 | React **18** + TypeScript 严格模式 + Vite + Tailwind CSS」
- 「后端 | Rust（stable），命令经 `#[tauri::command]` 暴露」
- 「存储 | SQLite + FTS5 + sqlite-vec（阶段三）；Markdown 文件（`prompt_engineering.md` / `memory.md`）」
- 「嵌入 | ONNX 本地推理；阶段一 `multilingual-e5-small`（~117MB / 384 维），记录 >200 条后换 `bge-m3`（1024 维，**换模型必须重建全库索引**，每条向量存模型名）」
- 「模型 | 三选一可配：`minimax` / `openai_compat` / `ollama`」
- 「插件 | 仅限 `global-shortcut`、`single-instance`、`autostart`、`clipboard-manager` 四个（**托盘图标属 Tauri 2 核心 `tauri::tray`，无独立插件**）」
- 「平台 | Windows 优先（可扩 macOS），**本期不做 Linux**」
- 「记忆 | `memory.md` ≤ **800 token** 硬上限；`candidate` 不参与注入；注入只带 `statement`+`why`+`how_to_apply`」
- 「版本控制 | git；`memory/` 目录每日提交」
- 禁止事项 1：「**禁止引入 Electron** 及任何 Node 进程常驻方案——常驻内存占用是本产品卖点。」
- 禁止事项 9：「**禁止在检索层未积累 20–30 条真实记录前引入向量库**（阶段一/二不得加 sqlite-vec 依赖调用路径）。」

**业务量与增长预估**：单机单用户；记忆条目阶段一 <50 条、阶段二 50–300 条、阶段三 300+ 条；PE 记录每日新增数条；嵌入与检索均在 CPU 上完成。

> **约束冲突处理**：ARC-01 输入提到 `tauri-plugin-tray-icon`，AGENTS.md 明确「托盘图标属 Tauri 2 核心 `tauri::tray`，无独立插件」，且插件清单固定为四个。**以 AGENTS.md 为准**：托盘走核心 `tauri::tray`，不引入第五个插件。
> **输入完整性**：现有输入足以支撑比较，无需提出澄清问题。
> **性能数据纪律**：本文不编造任何内存占用、召回率、延迟基准。除 ARC-01/《02-私人记忆库设计》已给出的输入值（`bge-m3` CPU 延迟 0.2–0.5s、e5-small ~117MB/384 维、bge-m3 ~570MB+/1024 维）外，所有量化阈值一律标注「需实测」，并进入 §五 待验证假设。

## 一、逐方案分析

### ①Tauri 2（React 18 + TypeScript + Vite + Tailwind CSS 前端 + Rust 后端）

**优势**

1. **直接命中「外壳 | Tauri 2」这条硬性约束**：唯一被 AGENTS.md 点名的外壳，「后端 | Rust（stable），命令经 `#[tauri::command]` 暴露」与「前端 | React **18** + TypeScript 严格模式 + Vite + Tailwind CSS」可 1:1 落地，无需改动任何既定栈。
2. **常驻内存税最低**：与 Electron 相比没有常驻 Chromium 与 Node 运行时，直接服务禁止事项 1「常驻内存占用是本产品卖点」——具体占用需实测（见假设 H2）。
3. **Windows 能力面完整**：`docs/01-案例调研与技术选型.md` §3.4 列出的五个 Windows 细节（点击穿透 `set_ignore_cursor_events`、不抢焦点 `set_focusable(false)`、多显示器 + DPI 的 `available_monitors()` / `current_monitor()` / `scale_factor()`、屏幕边缘自适应、`WS_EX_TOPMOST` 全屏处理）均有对应 API，且 AGENTS.md 依赖清单已含 `windows@0.62.2`。
4. **插件面不越界**：`global-shortcut` / `single-instance` / `autostart` / `clipboard-manager` 四个 + 核心 `tauri::tray`，恰好覆盖 AGENTS.md 允许的插件集，不需要额外插件。
5. **对「团队为 1 名个人开发者 + AI 编码 agent 协作」友好**：Web 前端 + Rust 后端是 AI agent 生成代码覆盖面最广的组合，且 React 组件化让 Pad UI 迭代快（《01》§3.1）。
6. **运维面最轻**：单文件 SQLite + `memory/` 纯 Markdown 目录，「版本控制 | git；`memory/` 目录每日提交」即可实现精确回滚，无需外部服务。

**劣势**

1. **Rust 学习成本落在单人身上**：Windows 专属能力（`WS_EX_TOPMOST`、多屏 DPI）必须写 Rust 侧代码，AI agent 生成的 Rust 代码需要人工审阅，返工成本高于 Electron/Python。
2. **托盘与部分窗口行为跨平台差异**：Tauri 官方 issue #116 指出 alwaysOnTop 与任务栏交互在 Linux 基本无解——本期不做 Linux，影响可控，但同类 Windows 边缘行为仍需实测。
3. **透明窗口阴影需自绘**：Windows 下 `shadow:false` 后需自行绘制，前端多一层实现工作（成本低，但确定存在）。
4. **升级/兼容风险外置**：Rust 依赖树（`tauri` / `rusqlite` / `reqwest` 等）的版本升级需人工把关，无法靠 JS 生态的宽松 semver 兜底。

**判定：在本约束下成立。** 它是唯一同时满足「外壳 | Tauri 2」「后端 | Rust（stable）」「前端 | React **18**」与四插件清单的方案，且没有引入任何禁止项。

### ②Electron（降级方案）

**优势**

1. **Windows 能力不设限**：`BrowserWindow` 的 `transparent` / `alwaysOnTop` / `frame:false` / `skipTaskbar` / `setIgnoreMouseEvents` 一应俱全（《01》§3.2），实现路径无死角。
2. **开发效率最高**：纯 Web 技术栈，前端与后端同语言，1 名个人开发者 + AI agent 的协作摩擦最小。
3. **Node 生态现成库最多**：任何桌面侧第三方能力都能直接 `npm install`，不存在「生态没得选」的硬伤。

**劣势**

1. **与硬性约束正面冲突**：AGENTS.md「外壳 | Tauri 2，**禁止 Electron**（除非某 Windows 能力绝对必需）」与禁止事项 1「**禁止引入 Electron** 及任何 Node 进程常驻方案——常驻内存占用是本产品卖点。」——除非能举证「某个 Windows 能力绝对必需」，否则不得选用。
2. **常驻内存是硬伤**：《01》§3.2 明确「一个 Pad 常驻后台却吃掉上百 MB RAM，说不过去」。Chromium + Node 主进程常驻，直接摧毁「TINY WHEN UNUSED」的产品原则。
3. **分发体积与升级成本上升**：安装包体积与运行时升级链路都比 Tauri 重（具体数值需实测）。
4. **故障面更大**：Chromium 多进程模型下，渲染进程卡死或主进程异常都可能拖垮常驻进程，排查成本高于 Rust 单进程。

**判定：在本约束下不成立。** 仅当出现「某个 Windows 能力绝对必需」且经代码级验证 Tauri 侧不可解时，才作为降级方案启用（触发信号见 §四）。

---

### ③PyQt/PySide

**优势**

1. **本地嵌入与 SQLite 生态顺手**：`sqlite-vec` 可直接 `pip install`，Python 侧做 ONNX 推理与检索原型最快（《01》§3.3）。
2. **单一语言贯通后端**：单人不必在 Rust / TS 之间切换心智负担，AI agent 生成 Python 的成功率也更高。
3. **桌面控件齐全**：QML / 信号槽在构建复杂桌面 UI 时表达力强。

**劣势**

1. **与「前端 | React **18** + TypeScript 严格模式 + Vite + Tailwind CSS」直接冲突**：选 PyQt/PySide 意味着放弃已定的 React 前端栈，改用 QML/Widgets，全量前端返工。
2. **窗口精细控制逊于 Tauri**：《01》§3.3 原文「透明无边框窗口的精细控制、多显示器 DPI 处理、打包体积都逊于 Tauri」——而这两项恰恰是本产品的核心体验（置顶不抢焦点、百分比坐标持久化、面板绝不出屏）。
3. **打包体积与依赖管理成本高**：需分发 Python 环境或依赖打包器，运维成本高于「单二进制 + 单文件 SQLite」的形态。
4. **崩溃隔离弱于 Rust**：解释器状态与 Qt 事件循环都可能产生「窗口还在但不响应」的难查故障。
5. **锁定风险最高**：绑定 Qt/Python 生态后，若后续要扩 macOS 或换栈，等于重写 UI 与后端。

**判定：在本约束下不成立。** 它以放弃既定 React 前端栈为代价，换来的收益（Python 生态顺手）在本项目只在「其余工具链全在 Python」时才成立——而本项目的既定栈是 React + Rust。

---

### ④`multilingual-e5-small`（~117MB / 384 维，ONNX 本地推理，CPU 可跑）

**优势**

1. **体积最小、链路最短**：~117MB 的 ONNX 模型是五个候选中唯一的「轻量嵌入方案」，索引体积与重嵌入成本都最低。
2. **完全满足「数据不出本机」**：ONNX 本地推理，嵌入阶段无任何网络调用——直接服务 AGENTS.md「嵌入 | ONNX 本地推理」与《02》的隐私约束。
3. **CPU 可跑**：与「嵌入与检索均在 CPU 完成」的预估一致，无需 GPU 依赖，运维成本低。
4. **阶段一/二根本用不到它**：阶段一纯 Markdown domain 路由、阶段二 FTS5 BM25 都不产生向量——选它意味着「不提前为用不到的能力付钱」，与禁止事项 9「**禁止在检索层未积累 20–30 条真实记录前引入向量库**」的意图一致。
5. **中文可用**：《02》§3.2 明确「默认首选，中文可用，CPU 即可跑」。
6. **对锁定风险的缓解有既定机制**：每条向量存储当时使用的模型名，换模型时可精确识别哪些需要重嵌入。

**劣势**

1. **语义召回弱于 `bge-m3`**：多语言/多粒度能力弱，中英混排场景的向量召回质量预计落后（《02》§3.2 的定性描述；本项目语料上的实际差距需实测，见假设 H1）。
2. **同质化**：384 维向量在长文本与细粒度区分上信息量更少，混合检索中的向量通道贡献可能偏低。
3. **切换成本前置存在**：一旦记录量超 200 条仍要换模型，重嵌入是一次性运维动作。

**判定：在本约束下成立。** 它是阶段一/二唯一无需为「尚未产生的能力」付代价的嵌入方案。

---

### ⑤`bge-m3`（~570MB+ / 1024 维，ONNX 本地推理，CPU 延迟 0.2–0.5s）

**优势**

1. **中英混排召回更强**：《02》§3.2 记录「多语言/多粒度，中英混排明显更强」，适合阶段三（300+ 条）后的混合检索。
2. **1024 维承载更多语义信息**，在向量 KNN + RRF 融合中可提供更强的语义通道。
3. **仍是 ONNX 本地推理**：不破坏「数据不出本机」，也无需 GPU。
4. **与 AGENTS.md 既定路线一致**：「记录 >200 条后换 `bge-m3`」是既定触发条件，不是新提案。

**劣势**

1. **起步阶段是纯粹的提前成本**：阶段一/二不产生向量，引入它等于为一个尚未存在的检索阶段付出 ~570MB+ 体积与更慢的 CPU 推理。
2. **迁移成本集中**：1024 维意味着**全库重嵌入**，且每条向量必须存储模型名——「**换模型必须重建全库索引**」，一次性运维动作明显大于 e5-small。
3. **CPU 延迟更高**（输入值 0.2–0.5s/条）：批量重嵌入与逐条检索都更容易触顶超时，夜间接口尤其明显。
4. **内存与分发体积抬升**：模型常驻内存 + 安装包体积同步上升（具体数值需实测）。
5. **锁定风险最高**：模型级锁定（向量库格式与模型绑定）叠加更高迁移成本。

**判定：在本约束下阶段一不成立、阶段三成立。** 作为阶段一起步方案属于提前引入向量库（与禁止事项 9 的意图相悖）；作为 PE 记录数 >200 条后的既定替换方案成立——该切换属于「既定阶段升级」，**不是**本决策的回退路径。

| **运维成本** | 最低——单二进制 + 单文件 SQLite + Markdown 记忆库，git 每日提交即可回滚，无外部服务 | 最高——多一个 Node 运行时与 Chromium 常驻，升级与分发链路更重（体积需实测） | 中等——需分发 Python 环境或打包器，依赖管理成本高于 Tauri | 低——~117MB 模型随应用分发，纯 CPU 推理，无 GPU、无额外服务 | 中——~570MB+ 模型抬升安装包与常驻内存，且换模型要触发一次全库重建索引 |
| **故障模式** | 少——无 Node/Chromium 常驻进程；主要故障点是置顶/点击穿透在多屏 DPI 与独占全屏下的表现，以及 provider 调用超时 | 多——Chromium 多进程 + Node 主进程任一子系统卡住都可能带崩常驻进程，透明置顶还多一层合成器变量 | 中——Qt 事件循环与解释器状态都可能造成「窗口还在但不响应」，崩溃隔离弱于 Rust | 低——纯 CPU 推理，失败模式是超时或模型文件缺失；常驻开销随模型体积走（~117MB 量级，需实测） | 低偏中——失败模式同上，但 CPU 延迟更高（输入值 0.2–0.5s/条），批量重嵌入时更易触顶超时 |
| **锁定风险** | 低——Rust + React 均为主流栈；自有 8 个 invoke 命令契约不依赖任何厂商 API 形态 | 低偏中——技术本身无锁定，但引入 Node 生态依赖并违背既定约束，返工成本即锁定成本 | 中——绑定 Qt/Python 生态，后续换栈几乎等于重写 UI 与后端 | 中——向量库每条存模型名，换模型须全库重嵌入，属模型级锁定；但 ONNX 运行时本身通用 | 中高——同 e5-small 且迁移成本更高：1024 维全库重嵌入 + 阶段三索引重建 |

**跨方案一致性检查**：Electron 与 PyQt/PySide 在「扩展性 / 查询能力 / 开发效率 / 运维成本 / 故障模式 / 锁定风险」六个维度上均不优于 Tauri 2 或 `multilingual-e5-small`，没有任何一个维度出现反转，因此不存在需要为个别维度另立方案的必要。

## 三、推荐结论与理由

### 3.1 唯一推荐

> **推荐方案（唯一）：Tauri 2 外壳 + 阶段一 `multilingual-e5-small` 嵌入。**
>
> 即：外壳保持 Tauri 2（React 18 + TypeScript + Vite + Tailwind CSS + Rust 后端 + 四插件 + 核心 `tauri::tray`）；嵌入模型阶段一/阶段二使用 `multilingual-e5-small`（~117MB / 384 维，ONNX 本地推理）；阶段三（PE 记录 >200 条）再按 AGENTS.md 既定路线切换 `bge-m3` 并重建全库索引。
>
> `bge-m3` 在本决策中是**阶段三的既定替换目标**，不是与本推荐并列的候选；Electron 是**降级方案**，仅在 §四 触发信号出现时启用；PyQt/PySide **不采用**。

### 3.2 三条理由（逐条引用 AGENTS.md 硬性约束原文）

**理由一 —— 外壳只能是 Tauri 2：Electron 被硬性约束直接禁止，PyQt/PySide 需牺牲已定前端栈。**
引用原文：「外壳 | Tauri 2，**禁止 Electron**（除非某 Windows 能力绝对必需）」；「前端 | React **18** + TypeScript 严格模式 + Vite + Tailwind CSS」。
在「某个 Windows 能力绝对必需」尚未被举证之前，Electron 无资格进入候选；而 PyQt/PySide 要成立就必须放弃 React 18 + TypeScript + Vite + Tailwind CSS 这条已定约束（改用 QML/Widgets 全量返工），并且《01》§3.3 已明确其「透明无边框窗口的精细控制、多显示器 DPI 处理、打包体积都逊于 Tauri」——而透明无边框与多屏 DPI 正是本产品的核心体验。

**理由二 —— 阶段一必须用 `multilingual-e5-small`，提前上 `bge-m3` 是在为不存在的能力付钱。**
引用原文：「嵌入 | ONNX 本地推理；阶段一 `multilingual-e5-small`（~117MB / 384 维），记录 >200 条后换 `bge-m3`（1024 维，**换模型必须重建全库索引**，每条向量存模型名）」；以及禁止事项 9：「**禁止在检索层未积累 20–30 条真实记录前引入向量库**（阶段一/二不得加 sqlite-vec 依赖调用路径）」。
阶段一纯 Markdown domain 路由（<50 条）、阶段二 FTS5 BM25（50–300 条）都不产生向量，此时 `bge-m3` 的 ~570MB+ 体积、1024 维存储与「全库重嵌入 + 每条向量存模型名」的迁移成本全部是净损失；`multilingual-e5-small` 以 ~117MB / 384 维满足「ONNX 本地推理」与「嵌入与检索均在 CPU 完成」，且符合禁止事项 9 的意图。

**理由三 —— Tauri 2 是唯一能同时满足「Rust 后端 + React 前端 + 四插件白名单 + Windows 优先」的组合。**
引用原文：「后端 | Rust（stable），命令经 `#[tauri::command]` 暴露」；「插件 | 仅限 `global-shortcut`、`single-instance`、`autostart`、`clipboard-manager` 四个（**托盘图标属 Tauri 2 核心 `tauri::tray`，无独立插件**）」；「平台 | Windows 优先（可扩 macOS），**本期不做 Linux**」。
Tauri 2 + Rust + React 18 + 四插件恰好对齐这条组合，不越界也不欠配；Electron 需新增 Node 运行时并违背禁止事项 1「**禁止引入 Electron** 及任何 Node 进程常驻方案——常驻内存占用是本产品卖点」；PyQt/PySide 需同时更换前端与后端语言栈。对「1 名个人开发者 + AI 编码 agent 协作」的团队，栈越少越贴近现有生成式工具链的覆盖面。

## 四、回退方案与触发信号

### 4.1 回退方案（唯一）

> **回退方案：外壳由 Tauri 2 回退到 Electron（降级方案）。**
>
> 适用范围：仅限 §3.2 理由一中的例外条款「除非某 Windows 能力绝对必需」。回退意味着**显式推翻 AGENTS.md 的硬性约束「外壳 | Tauri 2」**，必须先修改 AGENTS.md 并被用户确认，同时接受常驻内存上升与安装包体积变大（《01》§3.2：「常驻后台却吃掉上百 MB RAM，说不过去」）。
>
> **不属于回退的两项**（避免误用）：①`bge-m3` 替换 `multilingual-e5-small` 是 AGENTS.md 既定的阶段升级路径（触发条件：PE 记录 >200 条，且**换模型必须重建全库索引**）；②PyQt/PySide 不是回退目标——切换它等于重写前端与后端栈，代价高于回退 Electron。

### 4.2 触发回退的可观测信号

| # | 信号类型 | 触发条件（阈值 / 事件） | 判定与动作 | 阈值状态 |
|---|---|---|---|---|
| S1 | **事件型（首要）** | 出现「Tauri 2 无法实现、而 Electron 可实现」的**某个 Windows 能力绝对必需**：具体表现为——(a) 多显示器 + 混合 DPI 下「哪块屏 + 屏内百分比坐标」无法稳定落位；(b) 独占全屏应用下置顶窗口无法临时隐藏；(c) `Ctrl+Space` 全局热键在特定输入法或远程桌面组合下无法唤起。 | 每一条都必须产出**最小复现 + 代码级验证结论**（不是体感判断）。仅当结论为「Tauri 侧不可解且该能力为产品必需」时，才触发回退评估。 | 事件型，无需阈值 |
| S2 | **指标型** | `Ctrl+Space` **唤起成功率 < 99%**，且连续 **3 个工作日**出现同一失败模式（失败原因需分类记录：热键未注册 / 窗口未聚焦 / 进程被独占全屏抢占）。 | 命中率连续 3 日低于阈值 → 触发 Tauri 侧 Windows 能力缺口排查；排查结论若指向不可解，按 S1 处理。 | **初值建议，需实测校准**（尚无历史基线） |
| S3 | **指标型** | 面板从点击 DOT 到**可输入状态**的 P95 延迟 > **400 ms**，连续 3 个工作日，且经定位确认瓶颈在 Tauri 窗口/合成路径而非模型调用。 | 排除 provider 网络与模型推理因素后仍超阈值 → 评估回退。 | **初值建议，需实测校准** |
| S4 | **指标型（内存否决线）** | 常驻 idle RSS ≥ **100 MB**（依据《01》§3.2「吃掉上百 MB RAM 不可接受」）。 | 触发内存专项优化；**注意**：此项**不触发回退 Electron**（Electron 内存更高），只触发「外壳方案重新评审」——与 S1–S3 性质不同，单独记录。 | 依据文档定性表述推导，需实测确认 |

> 全部指标阈值均为**初值建议**：本项目尚无生产基线，必须在阶段一上线后用实测数据校准并固化（见假设 H2）。S1 是唯一无需阈值的硬性触发通道。

## 五、待验证假设清单

> 每条包含：验证方式 / 所需数据 / 判定标准。阈值均为初值建议，需实测校准。

### H1 · `multilingual-e5-small` 的中文短提示词语义召回足以支撑阶段二（以及是否真有必要等到 200 条才换 `bge-m3`）

- **验证方式**：从真实 PE 记录构造 50 条查询，人工标注每条查询的相关记忆条目；离线分别跑 FTS5 BM25 与 e5-small 向量检索，各算 Recall@5，对比两路差距与融合后的表现。
- **所需数据**：≥50 条真实 PE 记录（L1）、≥30 条 `status=active` 的记忆条目（L2）、50 条带标注查询集（标注工作量需单独估算）。
- **判定标准**：e5-small 向量路 Recall@5 ≥ **0.8**；且 e5-small + BM25 融合后的 Recall@5 **不低于**纯 BM25 超过 5 个百分点（百分点阈值需实测校准）。若融合增益 < 5 个百分点，则「记录 >200 条即换 `bge-m3`」的触发条件需重新标定（写入待确认清单）。

### H2 · Tauri 2 方案的常驻内存处于「TINY WHEN UNUSED」可接受区间

- **验证方式**：Windows 性能计数器采样——idle 状态连续 24 小时 RSS 时序 + 连续 200 次唤起/收起后的 RSS 峰值 + 模型加载前后的差值。
- **所需数据**：idle RSS 时序、峰值 RSS、唤起次数时间戳、是否已加载嵌入模型的标识。
- **判定标准**：idle RSS **< 100 MB**（依据《01》§3.2「吃掉上百 MB RAM 不可接受」）；峰值 RSS 上限需实测后固化。若 idle RSS ≥ 100 MB，先做内存专项优化（按 §四 S4 处理，不回退 Electron）。

### H3 · `bge-m3` 的 CPU 延迟（输入值 0.2–0.5s/条）不会让夜间全库重嵌入超出窗口

- **验证方式**：在目标机器上以 30 条 / 100 条两档做批量嵌入计时，记录单条 P50/P95 与总耗时；再叠加一次 FTS5 + sqlite-vec 索引重建。
- **所需数据**：目标机 CPU 型号与线程数、批量条数、耗时分布、索引重建耗时。
- **判定标准**：100 条全库重嵌入 + 索引重建总耗时 **< 30 min**（对齐 `run_nightly_job` 的超时设定），且**无单条超过 5 s**。超出则考虑分批 + 断点续跑，而非提前换模型。

### H4 · 「哪块屏 + 屏内百分比坐标」持久化在多显示器 + 混合 DPI 下不飘窗

- **验证方式**：矩阵测试——屏数 1/2/3 × 缩放 100%/125%/150% × 热插拔扩展屏，每种组合 20 次拖拽并记录持久化值与还原后的实际像素位置。
- **所需数据**：矩阵用例表、每次操作的 `monitor_index` / `x_ratio` / `y_ratio` 与还原后的实际位置、是否有出屏。
- **判定标准**：**出屏次数 = 0**，且面板始终完整落在目标屏幕可视区内；热插拔后坐标必须落在有效屏范围内（越界时回退到主屏默认位置）。

### H5 · 1 名个人开发者 + AI 编码 agent 能在 Rust / Tauri 栈下维持交付节奏

- **验证方式**：记录实施路线前 4 步（透明窗口 → 常驻 DOT → 展开收起 → 改写闭环）的实际工时、git 提交数与返工条目，并按「跨语言边界（TS ↔ Rust）」分类统计返工原因。
- **所需数据**：每步起止时间、提交记录、返工条目与原因分类。
- **判定标准**：单步交付 ≤ **1 个工作日**，且因跨语言边界导致的返工 ≤ **1 次/步**（两项阈值均需实测校准）。若显著超出，重新评估「命令契约（8 个 invoke）是否过细」这一契约粒度问题，而非直接换栈。

## 六、决策复盘触发条件

本决策在以下任一情况出现时必须重新评审：

1. §四 的 S1 事件型信号被确认（存在「Tauri 不可解、Windows 能力绝对必需」）。
2. 假设 H2 被证伪（idle RSS ≥ 100 MB）且内存专项优化无效。
3. PE 记录数 **> 200 条**（AGENTS.md 既定的 `bge-m3` 切换阈值）——届时需按假设 H1 的实测结论确认「换模型 + 重建全库索引」的实际成本。
4. 目标平台从「Windows 优先」扩展到 macOS 或需要 Linux 支持（本期明确不做 Linux）——此时外壳的跨平台能力需要重新实测。
