# Prompt Pad · 私人记忆库设计

> 目标：让提示词在本机上**越用越聪明**——每次优化都在为下一次优化积累经验。
> 核心原则：**对话是草稿，文件是大脑；AI 不记住任何事，AI 只记住「去哪里找」。**

---

## 一、四层记忆架构

把「原始记录」和「泛化规则」严格分开，是整个设计的地基。

| 层 | 载体 | 内容 | 体积 | 生命周期 |
|----|------|------|------|---------|
| **L0 临时层** | 对话上下文 | 本次会话 | 最小 | 会话结束即弃 |
| **L1 事实层** | `prompt_engineering.md` | 提示词原文、优化策略、使用结果 | 随用随长，无上限 | **永久，逐字不可改** |
| **L2 记忆层** | `memory.md` | 从 L1 提炼的可泛化规则 | **严格受限（≤800 token）** | 晋升 / 降级 / 废弃 |
| **L3 索引层** | SQLite（索引库） | L1/L2 的全文 + 向量索引 | 可重建 | 随内容增删 |

**为什么必须分层**：如果把记忆和原文混在一起，上下文预算会被历史案例吃光，模型反而变笨。WorkBuddy 官方文档反复强调同一个教训——**别让冗余定义吃掉上下文窗口**。

**L1 → L2 的晋升门槛**：一条 L1 记录产生的信号，只有在**被验证过至少一次**后才允许晋升为 L2 记忆。未验证的候选规则留在 L1 的 `signals` 字段里，不进入注入集。

## 二、memory.md 格式规范

### 2.1 文件头

```yaml
---
format_version: 1
token_budget: 800          # 硬上限，超出即拒绝晋升
domain: <global>
updated: 2026-10-14
entry_count: 0
active_count: 0
deprecated_count: 0
---
```

### 2.2 记忆条目

每条记忆必须有**唯一 ID、明确陈述、来源凭据、可计算的权重**。

```markdown
## M-<域缩写>-<序号> · 一句话规则名

- **type**: rule              # rule | preference | pitfall | asset
- **domain**: ui-design       # 与 L1 的 domain 对齐，用于路由
- **status**: candidate       # candidate | active | deprecated
- **statement**: 当任务涉及品牌色时，必须把不可替换的品牌色单列为「硬性约束」，把「需要更多变化」写为软偏好并显式声明不得替代主色。
- **why**: 防止模型用生成的色彩替换品牌主色，导致品牌识别崩塌。
- **how_to_apply**: 在提示词中单开一章「硬性品牌约束」，逐条列出不可违反项。
- **signals**: [S-HARD-SOFTSPLIT]
- **evidence**: [PE-2026-001]        # 来源记录，可追溯到原文
- **weight**: 0                       # 成功次数 − 失败次数，由系统自动维护
- **hits**: 0                         # 被注入的次数
- **last_used**: null
- **created**: 2026-10-14
```

### 2.3 字段设计意图

| 字段 | 为什么必须有 |
|------|-------------|
| `statement` | 一条规则**只允许说一件事**。写成两件事的规则无法判断成败，也就无法计算权重 |
| `why` | 注入时带上原因，模型才知道什么时候该用这条而不仅是硬套 |
| `how_to_apply` | 直接给出可复制的提示词片段——这是**让记忆真正作用于输出的关键** |
| `evidence` | 没有来源的记忆是幻觉。必须能回溯到某条真实记录 |
| `weight` | **这是「越用越聪明」的核心**。权重由真实成败累积，不由人工设定 |
| `status` | 让系统可以自动淘汰垃圾规则，避免记忆库无限膨胀 |

### 2.4 状态机

```
candidate ──(weight ≥ 2 且无失败)──> active ──(weight < −1 或连续 3 次任务未命中)──> deprecated
    │                                   │
    └──(验证失败)──> deprecated          └──(被更强规则取代)──> deprecated
```

- **candidate**：刚提炼，尚未证实，**不参与注入**
- **active**：已证实有效，**参与注入**
- **deprecated**：保留存档但不注入，且不占用 token 预算

## 三、检索策略

### 3.1 双路召回

单一检索方式都不够用：

- **全文检索（FTS5 / BM25）**：搜「摘要」找不到写「文章总结」的记录。快、准，但只认词面。
- **语义检索（向量）**：能跨表述找到同类，但需要嵌入模型，且可能召回语义相近但实际无关的内容。

成熟做法是**两路并行 + RRF 融合**。参考开源项目 obsidian-hybrid-search 的实测：BM25 列权重设为 title 10× / aliases 5× / content 1×，与 trigram 模糊匹配、sqlite-vec 向量 KNN 三路并行，再用 Reciprocal Rank Fusion 合并并归一化到 0-1。在 171 篇笔记 / 58 条查询的基准上 nDCG@5 为 0.733；换用 bge-m3 在 22,419 条记忆的 LongMemEval-S 上可达 0.895。

### 3.2 本地嵌入模型选型

| 模型 | 体积 | 维度 | 特点 |
|------|------|------|------|
| multilingual-e5-small | ~117 MB | 384 | 默认首选，中文可用，CPU 即可跑 |
| bge-m3 | ~570 MB+ | 1024 | 多语言/多粒度，中英混排明显更强，CPU 可跑但延迟 0.2-0.5s |

**建议**：先上 e5-small 跑通链路，记录量超过 200 条后再换 bge-m3。换模型时必须**重建全库索引**（每条记录要存下当时用的模型名，否则无法判断哪些需要重嵌入）。

### 3.3 注入预算与路由

1. **硬性规则**（domain 与当前任务匹配、status=active、weight>0）→ 按 weight 降序取 Top-K
2. **注入前裁剪**：只注入 `statement` + `why` + `how_to_apply`，**不注入 evidence 和统计数据**（那是给我们自己看的，不是给模型的）
3. **总量控制在 800 token 以内**，超预算则按 weight 从低到高裁剪
4. 若无匹配记忆，**明确告诉模型「暂无历史经验」**，而不是塞入低分噪声

> 这一步最容易被忽略。检索结果 Top-10 全量注入，比不注入更糟——噪声会稀释强信号。

## 四、自动沉淀流程

WorkBuddy 的做法是**每晚自动从当天对话中提取记忆，用户零操作**。这是对的——让用户手动维护记忆库，一定坚持不下来。

### 4.1 夜间任务流水线

```
1. 扫描当天新增的 PE 记录
2. 对每条记录的 signals 去重、合并
3. 与现有 memory.md 条目做相似度匹配
   ├─ 匹配到已有条目 → 权重 +1，补充 evidence
   ├─ 无匹配且 weight 达标 → 新建 candidate
   └─ 无匹配但与已有条目矛盾 → 标记冲突，挂起待人工裁决
4. 检查 token_budget，超出则从 weight 最低的 deprecated 起裁剪
5. 重建/增量更新索引库
```

### 4.2 权重更新（每次 Pad 使用后立即执行）

| 事件 | weight 变化 |
|------|-------------|
| 注入的记忆被模型采纳，输出质量被用户认可（评分 ≥4） | +1 |
| 注入了但输出无明显改善 | 0 |
| 注入了但导致输出变差或模型跑偏 | **−2**（惩罚要大于奖励，坏经验的危害大于好经验的收益） |
| 该次任务未检索到该条记忆 | hits 不变，触发「连续未命中」计数 |

### 4.3 防污染机制（必须有）

自动沉淀最大的风险是**垃圾自动进、垃圾自动扩散**。四道防线：

1. **人工裁决闸门**：矛盾条目、跨 domain 推广的条目，一律挂起不自动写入
2. **候选不注入**：新提炼的规则先在 `candidate` 状态，至少被验证 2 次才升 `active`
3. **全量可读**：memory.md 是纯 Markdown，随时能打开看、能手改、能 diff。**绝不让记忆只存在于向量库里**——向量库里的 embedding 是不可读的，你无法知道 AI「记住了什么」
4. **版本控制**：整个 `memory/` 目录纳入 git，每日一提交。出问题时能精确回滚某条规则的引入

> 第 3 条与第 4 条参考开源项目 self-improving-agent 的实践：它把记忆直接写成 `.learnings/ERRORS.md`，理由正是「完全透明、Markdown 可 git 管理，打开就知道 Agent 记住了什么、什么时候记的」。

## 五、冷启动

新装的 Pad 记忆库是空的，此时所有 `weight = 0`，没有任何记忆可注入。三个填充路径：

1. **批量回填**：把历史记录导入 `prompt_engineering.md`，跑一次夜间任务批量提炼候选规则
2. **AI 迁移**：抄 WorkBuddy 的做法——让用户在常用 AI 里生成一份「关于我的偏好总结」，检查后导入为 `preference` 类记忆
3. **冷启动豁免**：前 10 次使用不做权重惩罚，只收集数据

## 六、演进路线

| 阶段 | 存储 | 检索 | 适用规模 | 成本 |
|------|------|------|---------|------|
| **一**（推荐起步） | 纯 Markdown：L1 + L2 | 无检索，靠 domain 路由 | < 50 条 | 零，100% 精确 |
| **二** | Markdown + SQLite FTS5 | 关键词 + 模糊匹配 | 50-300 条 | 极低 |
| **三** | Markdown + SQLite + sqlite-vec | 混合检索 + RRF + 重排 | 300+ 条 | 中，需本地嵌入模型 |
| **四** | 图数据库 + 向量库 | 关联推理 + 时间衰减 | 多 Agent / 团队 | 重，需要独立服务 |

**明确建议从阶段一开始。** 理由：阶段一的 token 消耗最低、结果 100% 可控可解释，而且**只有在积累了几十条真实记录之后，你才知道自己到底需不需要模糊检索**。过早引入向量库只会让你在检索效果不佳时无法判断是模型的问题还是数据的问题。

对比参考：MemOS 走的是 Neo4j + Qdrant 的工业路线（本地版用 SQLite + 混合搜索），官方对比 OpenAI Memory 称准确率 +43.70%、token 消耗 −35.24%。这条路对个人单机 Pad 明显过重，等真到了阶段四再考虑。
